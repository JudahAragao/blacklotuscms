# Theme Engine Specification

## Description
Theme engine based on React Server Components with CSS scoping via build-time bundling, generated static imports, CSS variables, permissions system for data access, ACF-style helpers for custom fields, and dual-store context (React.cache + AsyncLocalStorage) for resilience in async boundaries.

## Requirements
- **REQ-01:** Static import of layouts via `theme-registry.ts` generated by `themes:generate`
- **REQ-02:** Customizable CSS Variables via theme's `style.css`
- **REQ-03:** CSS scoping via selector replacement (`.blacklotuscms-theme` → `.blacklotuscms-theme[data-bl-theme="id"]`) + native `@scope` for Chrome 118+
- **REQ-04:** ThemeDataService with permission validation
- **REQ-05:** Dual-store context: React.cache as primary store (survives unstable_cache boundaries) + AsyncLocalStorage as fallback (test compatible). getThemeStore() prioritizes React.cache when themeName is set
- **REQ-06:** Data sanitization before passing to theme
- **REQ-07:** Theme permission requests (pending/approved/denied)
- **REQ-08:** `theme.json` as theme manifest with `themeApiVersion: 1`
- **REQ-09:** Automatic `@keyframes` namespacing with `bl-<id>-` prefix
- **REQ-10:** CSS token validation: declared vs. used in build
- **REQ-11:** Theme helpers (get_field, the_field, have_rows, get_rows, get_sub_field, the_sub_field, get_row_index, get_field_object, get_field_name, get_field_type, acf_add_local_field_group)
- **REQ-12:** Dynamic layout resolution by slug or ID (slug matches theme-exported layout = automatic context; fallback to ID when slug not found)
- **REQ-13:** WordPress-style template hierarchy: post.{type} → post → default.post fallback chain
- **REQ-14:** Automatic synchronization: page.tsx and ThemeRenderer set getReactStore() after themeStorage.run() to ensure ThemeDataService works even if AsyncLocalStorage is lost
- **REQ-15:** Custom routes via theme's `routes.json` with dynamic params support (`:slug`, `:id`, etc.)
- **REQ-16:** RouteService for URL → template + params pattern matching (resolution: plugin routes → theme routes → default theme routes → CMS default)
- **REQ-17:** ThemeRenderer accepts `routeParams` prop and passes it to layout components
- **REQ-18:** RouteContext includes authenticated user's `role` (name + capabilities) for template personalization

## User Roles
- **Administrator:** Manage themes (enable/disable via panel)
- **Themes:** Access data via ThemeDataService with validated permissions

## Constraints
- **C01:** Themes only access data with approved permissions
- **C02:** Theme name is sanitized with `sanitizePath`
- **C03:** Data passed to theme is masked (`maskSensitiveData`)
- **C04:** Fallback to "post" layout if import fails
- **C05:** Themes are source-controlled — no upload, installation, or runtime editing
- **C06:** `:root` is converted to `:scope` in CSS; use of `html`/`body` is prohibited
- **C07:** `predev`, `prebuild` and `pretest` automatically run `themes:generate`

## Build Pipeline

1. Script `scripts/generate-theme-registry.mjs` discovers folders in `themes/`
2. For each theme, reads `theme.json`, `theme.ts`, `style.css` and `routes.json`
3. Validates manifest, `themeApiVersion`, declared vs. used CSS variables
4. Namespaces `@keyframes` with `bl-<id>-` prefix
5. Generates `src/generated/theme-registry.ts` (static layout imports)
6. Generates `src/generated/theme-styles.css` (isolated CSS with selector replacement + `@scope`)
7. Generates `src/generated/theme-routes.ts` (per-theme custom routes)

## Dependencies
- **Depends on:** Post Management, ThemeDataService
- **Blocks:** NONE (main public feature)
- **Related to:** Plugins, Security
