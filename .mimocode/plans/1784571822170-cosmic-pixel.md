# Compiled Plugins System (Alternative to isolated-vm)

## Context

The current plugin system uses isolated-vm (V8 sandbox) which prevents plugins from using npm packages. Next.js 16 compiles everything at build time with no runtime build step. This plan adds a **second plugin type**: compiled plugins that live in the `plugins/` directory, are compiled alongside Next.js, and can use any npm package already in the project. Both types coexist.

## Architecture

```
plugins/                          # Compiled plugins (in repo, built with Next.js)
├── email-manager/
│   ├── plugin.json               # Manifest with permissions + npm dependencies
│   └── index.ts                  # Entry point, exports default function
└── seo-plugin/
    ├── plugin.json
    └── index.ts

src/generated/plugin-registry.ts  # Generated: static imports + metadata
src/core/sandbox/CompiledPluginLoader.ts  # Loads compiled plugins with Proxy
```

**Flow:**
1. Developer adds plugin to `plugins/` folder with `plugin.json` + `index.ts`
2. `npm run plugins:generate` reads all plugins, generates `plugin-registry.ts`
3. `npm run build` compiles everything (Next.js + plugins together)
4. Admin activates plugin in panel → permissions requested → plugin loads

## Files to Create

### 1. `scripts/generate-plugin-registry.mjs` (NEW)

Similar to `generate-theme-registry.mjs`. Discovers plugins in `plugins/`, reads `plugin.json`, generates `src/generated/plugin-registry.ts`.

```
Input: plugins/*/plugin.json
Output: src/generated/plugin-registry.ts
```

The generated file contains:
- Static imports for each plugin's `index.ts`
- Plugin metadata (name, version, description, permissions)
- A registry object mapping plugin name → { init function, manifest }

**Validation:**
- Plugin name must be kebab-case
- plugin.json must have `name`, `version`, `entry` (default: `index.ts`)
- Permissions array is read and stored in registry
- Duplicate plugin names → build error

### 2. `src/generated/plugin-registry.ts` (GENERATED)

```typescript
/* Generated by scripts/generate-plugin-registry.mjs. Do not edit. */
import * as Plugin0 from '../../plugins/email-manager/index';
import * as Plugin1 from '../../plugins/seo-plugin/index';

export interface CompiledPluginManifest {
  name: string;
  version: string;
  description?: string;
  permissions: string[];
}

export interface CompiledPluginEntry {
  init: (bridge: any) => Promise<any> | any;
  manifest: CompiledPluginManifest;
}

export const pluginRegistry: Record<string, CompiledPluginEntry> = {
  "email-manager": {
    init: (Plugin0 as any).default,

  },
  "seo-plugin": {

  },

export const compiledPluginNames = ["email-manager", "seo-plugin"] as const;
```

### 3. `src/core/sandbox/CompiledPluginLoader.ts` (NEW)

Loads compiled plugins with a Proxy-based bridge. Each plugin receives a controlled `bridge` object.

**Key behavior:**
- Plugin's `init(bridge)` function is called with a frozen bridge
- Bridge methods check permissions from the plugin's manifest before executing
- Plugin cannot access `require`, `process`, `__dirname`, `globalThis` (they don't exist in scope)
- Plugin CAN import npm packages that are in the project's `node_modules` (compiled by Next.js)

**Bridge Proxy structure:**
```
bridge.log(...args)              → console.log with plugin prefix
bridge.db.read(model, query)     → permission check → prisma[model].findMany
bridge.db.findOne(model, where)  → permission check → prisma[model].findFirst
bridge.db.create(model, data)    → permission check → prisma[model].create
bridge.db.update(model, where, data) → permission check → prisma[model].update
bridge.db.updateMany/deleteMany/delete/upsert/transaction → same pattern
bridge.http.request(config)      → permission check http.outbound.request → fetch
bridge.storage.get(key)          → pluginDataService.get(pluginId, key)
bridge.storage.set(key, value)   → pluginDataService.set(pluginId, key, value)
bridge.hooks.addAction(name, cb) → hookService.addAction(name, cb, pluginId)
bridge.hooks.addFilter(name, cb) → hookService.addFilter(name, cb, pluginId)
bridge.webhook.on(event, cb)     → networkService.registerWebhookHandler
bridge.routes.register(config)   → routeService.registerPluginRoute
bridge.permissions.request(cap)  → pluginDataService.requestPermission
```

**Permission flow on activation:**
1. Admin clicks "Ativar" on compiled plugin
2. PluginService reads manifest from pluginRegistry
3. For each permission in `manifest.permissions`, create a pending PluginPermission record
4. Admin sees all pending permissions in the plugins panel
5. Admin approves/denies each one
6. Once all approved → plugin loads with full bridge access
7. If any denied → plugin doesn't load, shows which permissions are missing

### 4. Modifications to `src/core/services/PluginService.ts`

Add methods to handle compiled plugins alongside existing isolated-vm plugins:

- `activateCompiled(pluginName, user)` — loads from pluginRegistry, requests permissions, calls init(bridge)
- `deactivateCompiled(pluginName, user)` — disposes, cleans up hooks/routes/webhooks
- `bootCompiledPlugins()` — on startup, loads all active compiled plugins
- The existing `activate()`/`deactivate()`/`boot()` remain for isolated-vm plugins

**Activation flow for compiled plugins:**
```
Admin clicks "Ativar"
  → activateCompiled(pluginName)
  → Read manifest from pluginRegistry[pluginName]
  → Check if all permissions are approved
  → If not: create pending permissions, throw error listing missing ones
  → If yes: create bridge via createBridgeApi(pluginId, manifest)
  → Call pluginRegistry[pluginName].init(bridge)
  → Mark plugin as isActive in DB
```

## Plugin Developer Experience

### Creating a compiled plugin

```bash
# 1. Create plugin directory
mkdir plugins/my-plugin

# 2. Create plugin.json
cat > plugins/my-plugin/plugin.json << 'EOF'
{
  "name": "my-plugin",
  "version": "1.0.0",
  "description": "My awesome plugin",
  "permissions": ["db.read.post", "db.write.post", "http.outbound.request"],
  "npmDependencies": ["lodash", "date-fns"]
}
EOF

# 3. Create index.ts
cat > plugins/my-plugin/index.ts << 'EOF'
import { Resend } from 'resend';

export default async function init(bridge: any) {
  bridge.hooks.addAction('post.created', async (post: any) => {
    const user = await bridge.db.findOne('User', { id: post.authorId });
    const apiKey = await bridge.storage.get('api_key');
    const resend = new Resend(apiKey);
    await resend.emails.send({
      from: 'noreply@site.com',
      to: user.email,
      subject: `New post: ${post.title}`,
      html: `<h1>${post.title}</h1>`
    });
  });

  return { name: 'my-plugin', version: '1.0.0' };
}
EOF

# 4. Run build
npm run build
```

### Activating in admin

1. Admin goes to Plugins panel
2. Sees "my-plugin" in "Compiled Plugins" section
3. Clicks "Ativar"
4. Modal shows: "This plugin requires: db.read.post, db.write.post, http.outbound.request"
5. Admin confirms → permissions created as "pending"
6. Admin approves each permission in the "Solicitacoes de Acesso" section
7. Plugin activates, hooks register, routes register
